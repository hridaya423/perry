# Typed execution-plan synthesis

This is the implementation sketch for M1, not evidence that M1 is complete. Both candidates were read in full and independently compared. The selected contract still needs executable migration and integration tests before production cutover.

## Decision

Use candidate B's PerryRuntimes-owned executable plan and attempt-aware journal model. The independent reviewer scored B 20/25 and A 18/25, favoring B's explicit uncertain state and its fit with the existing runtime boundary. The parent initially favored A to avoid a second task-identity representation. That concern is resolved by moving the shared `TaskID` value to PerryCore rather than inventing B's `ExecutionTaskID` conversion. Core retains shared identity and trust vocabulary; executable operations and their codec live with planner, executor, and verifier contracts in PerryRuntimes. TaskCoordinator in PerryGuide owns durable state.

Keep B's separation between approval requirement and issued grant, and its coordinator-owned `prepared → dispatched → verified` journal. Graft A's registered executable identity and binding of approval to action contents. Each operation owns its target; remove B's duplicate top-level target. Preserve one canonical action through all three runtime interfaces. Decoding must enforce the relationship between operation, required scopes, and postcondition.

The parent's initial scores, before resolving the identity-ownership concern, were:

| Criterion | A | B | Remaining constraint |
| --- | ---: | ---: | --- |
| Parameter preservation and migration | 3 | 3 | Neither draft supplies executable v1/v2 migration fixtures. |
| Approval binds the exact effect | 3 | 3 | The grant must bind operation contents, account identity, confinement, and target, not IDs alone. |
| Durable recovery | 3 | 4 | Persist dispatch intent before invoking the effect; do not infer verification from execution success. |
| One canonical action | 4 | 4 | Delegated coding tasks cannot remain an untyped execution escape hatch. |
| Module and interface simplicity | 3 | 2 | A avoids a second task identity; both need reconciled caller signatures and fewer redundant fields. |

The independent scores for A/B were 4/4 for preservation, 4/3 for approval, 3/5 for recovery, 4/4 for the canonical pipeline, and 3/4 for module ownership. Neither review treated the score as a passing implementation gate. The chosen synthesis keeps B's stronger journal contract while correcting the authority, target, and identity issues rather than adopting either draft unchanged.

## Contract corrections

`ExecutionPlan` keeps `schemaVersion`, `planID`, `taskID`, the user goal, typed actions, and requested scopes. A constructor and the decoder share structural validation and throw on invalid external values; malformed data must not reach a precondition trap. Identical action IDs cannot identify different effects within a plan. Steering creates a new immutable plan identity and invalidates grants for the superseded plan.

Computer actions carry the exact bundle ID, process ID, window ID, and Cua connection generation. Element selectors and window-pixel coordinates remain typed operation inputs. A stale generation requires a new binding and approval where necessary; a label or window title cannot silently substitute a different target. Existing passive guide highlights remain guide presentation operations, not delegated execution.

File operations retain exact UTF-8 contents, relative paths, and directory/file distinctions. Core validates lexical paths; the executor owns filesystem confinement and the verifier owns read-back. Use a String for text rather than an additional pass-through text wrapper. Directory creation verifies directory type. File creation verifies exact bytes and file type. Rename and trash need identity-aware postconditions; existence checks alone do not establish that the intended item moved.

An existing window is not proof of a successful click, and a provider's generic acceptance is not proof that the intended resource changed. Postconditions must identify the expected text, element state, visual change, file result, or provider resource result. Unsupported verification ends blocked, never verified. Shell exit zero is process-completion evidence; it does not establish the user-requested result without its declared postcondition.

Keep sandboxed coding-agent tasks within the typed execution boundary. A registered executable command and a coding task are distinct launch descriptions under `SandboxedCommand`. The coding-task description retains the selected verified runtime binding, exact task text, workspace identity, confinement policy, declared effects, and postcondition. The runtime adapter constructs official CLI arguments. Unknown planner output cannot select this path. A legacy delegate lacking sufficient confinement or authority remains retained and non-resumable; this migration rule does not remove new, explicitly authorized Codex tasks from the product.

Approval grants bind the task and immutable plan, approved action contents, exact targets and provider account, requested scopes, and the executable/confinement binding. Runtime health timestamps and latency measurements are not authority inputs. Use one canonical encoding for the digest; unordered scope sets must serialize deterministically. Avoid candidate A's separate digests for overlapping copies of the same effect. A supplied grant is checked against current revocation state before dispatch, not reconstructed from Settings.

TaskCoordinator writes the prepared action and its grant/checkpoint transactionally, then persists dispatch intent before the executor runs. The executor returns a transient result. Only verified evidence advances the checkpoint and records `verified` in the same durable envelope. An interrupted dispatched action stays uncertain even if its declaration says it is idempotent. Neither a successful subprocess exit nor a returned HTTP response independently advances the task.

## Migration and verification order

The store migration uses one `TaskPlan` sum with legacy and executable cases inside the existing `TaskRecord`; it does not introduce a second task map or convert executable actions back into string payloads. Outer store version three distinguishes this representation from the executable plan's own schema version one. Version-one and version-two records remain legacy after decoding, including their approval and uncertain-dispatch checkpoints.

Admission now compares a persisted mutation identity and retrieves the coordinator's stored record rather than trusting the caller's payload. Each mutation receives a fresh UUID: the coordinator permits removing a task and later reusing its ID, so a reset counter could let an old request match a replacement record. Plan digests continue to bind approval, while mutation identity detects stale control requests. The runner switches on the plan representation before selecting an executor, and background presentation reads action summaries without manufacturing legacy steps. The local planner's single-file background route now uses typed plans, a revision-bound approval sheet, the durable journal, and history-before-removal reporting. Other task families still use legacy execution.

1. Add the canonical values and deterministic codec, preserving task/action ID encodings. Prove round trips for exact UTF-8 bytes, target identities, typed provider operations, sandbox bindings, and questions; malformed or unknown variants must throw before any effect.
2. Add v1/v2 task-envelope fixtures containing checkpoints, suspended approvals, cancellation intent, and uncertain dispatch. Migration either preserves every execution-relevant value and identity or retains the original record with a non-resumable disposition. Do not infer authority or targets from summaries.
3. Move the workspace planner/executor/verifier slice to the canonical action and run it through persistence, approval, execution, and exact read-back. Add denied-approval and crash-after-dispatch traces at the same boundary.
4. Move Cua and the existing typed integration catalog, then the remaining planner/runtime adapters. New provider operations remain M6 work; an enum declaration alone is not implementation evidence.
5. Remove metadata-only plan adapters, summary-to-readWindow migration, and legacy execution overloads only after production callers and migration tests no longer rely on them. Keep the old serialization reader for retained legacy records.

The independent comparison is complete. The implementation begins with the canonical values and codec; caller migration must preserve the existing behavior until its boundary tests pass. The old PerryCore metadata plan and its consumers may be explicitly module-qualified during this transition, but they must be removed before M1 is accepted. This is a temporary source migration, not two supported production plan formats.

The implementation gate requires the real boundary tests above, an independent code critique, and reproduced build/test evidence. Neither the design review nor codec tests substitute for the live M1–M11 release requirements.
